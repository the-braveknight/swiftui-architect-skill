# SwiftUI Architect

Decides where code lives, who owns it, and the shape of the pieces that hold a modular SwiftUI app together. For how to write the SwiftUI or concurrency code inside those shapes, use the skills in [Related skills](#related-skills).

`X` stands for a feature, named for its capability (`Discover`, `Movie`), or for one of its screens (`MovieDetail`, `MovieCast` → `MovieCastService`, `MovieCastViewModel`, `MovieCastView`, `MovieCastScreen`). A *screen* is one navigable page: the feature exports its view, and the app composes it in an `XScreen`. The examples are a movie browser on the TMDB API.

## The shape

```
App target              composition root: services, screens, routing
│
├── Feature packages    one per capability (Discover, Search, Movie, …)
│     XCore     domain models, errors, a service protocol and mock per screen
│     XUI       view models, views, XDestination, strings
│     XLive     live services: API responses → domain models
│     XTests    view model and mapping tests
│
└── Shared packages
      Core          domain vocabulary several features share (Foundation only)
      CoreUI        views several features show, built on Core and DesignSystem
      DesignSystem  domain-free tokens, styles and components
      Networking    the API client, generated by Apple's swift-openapi-generator
```

## Dependency direction

Each module may import only what its arrow points at. Nothing points back up, and features never point at each other.

```
App ──────► XCore, XUI, XLive, Core, DesignSystem, Networking
XUI ──────► XCore, Core, CoreUI, DesignSystem
XLive ────► XCore, Core, Networking
XCore ────► Core
XTests ───► XCore, XUI, XLive, Core, CoreUI, Networking
CoreUI ───► Core, DesignSystem
Core, DesignSystem, Networking ──► Apple frameworks and their own dependencies only
```

Hard rules:
- A feature never imports another feature. Navigation between features goes through the app; a feature that needs another's data declares a port the app implements.
- XCore never imports SwiftUI or Networking. Domain models describe what the app shows, not what the API returns.
- Generated API types never leave XLive. Live services map them to domain models, and transport errors to the feature's errors.
- DesignSystem knows no domain: no feature models, services or destinations.
- The app is the only module that sees every feature, so it is the only place features meet.


## Who owns what

| Concern | Owner |
|---|---|
| Domain models, errors, a service protocol and mock per screen | Feature: `XCore` |
| Live services, mapping API responses and errors to the domain | Feature: `XLive` |
| View models, views, strings, where its views can go (`XDestination`) | Feature: `XUI` |
| The places several features open (`CoreDestination`) | `CoreUI` |
| The generated API, the client over it, error classification | `Networking` |
| Building the client and services, injecting them | App: `XApp.init`, through the environment |
| Building a screen: reading services, creating view models | App: one `XScreen` per screen |
| Navigation state, and which screen each destination shows | App: `Router`, `Destination`, `DestinationView` |
| Sheets, covers and alerts, and what a sheet edits before it's applied | The presenting screen's view model, as plain `var`s its views bind |

## Principles

1. **Features own their screens' views; the app composes and routes them.** A feature never builds or shows another feature's screen.
2. **Models speak the app's language.** Each is shaped for what a screen shows and can't hold an illogical value; the API's shape stops at XLive.
3. **Services do the work; view models hold state.** A service returns view-ready domain values; a view model assigns them and manages loading, errors and paging.
4. **Feature views stay plain and native.** They receive a view model, render it, and push values with `NavigationLink(value:)`. No routers, navigation closures or service lookups in feature views.
5. **Duplicate before you share.** A type moves to Core or CoreUI only when a second feature needs the same concept and both copies must change together.
6. **Every module builds, previews and tests on its own.** XCore ships a mock of each service, so XUI needs nothing else.
7. **Native SwiftUI, nothing invented.** No navigation libraries, DI containers, wrapper views around stacks, or infrastructure the app doesn't need.
8. **One screen per kind of content.** When the things a feature opens load, page or search differently, each gets its own screen, rather than one detail screen that switches on what it was given.

## The shapes in brief

- **Models and errors.** Domain models are `Equatable`, `Sendable` values shaped for what screens show (`Movie`, and `MovieSummary` for a list). Each feature has its own error enum, cased by what its screens show (`offline`, `notFound`, `unavailable`); an empty answer is never an error.
- **Services.** XCore declares a service protocol per screen that returns view-ready domain values (`Page<Item>` for a paged list) and throws the feature's error; a concern with a source of its own, such as searches kept on the device, is a service of its own. XLive implements each over the networking client and maps responses and errors into the domain. XCore ships a mock of each (`.mock`).
- **View models.** `@MainActor @Observable public final class XViewModel`, one per screen (a pushed view or a tab's root), built by the app with IDs and services. Each resource has its data, `isLoading…` and `…Error`; a paged one adds `next…Page`, `isLoadingNext…Page` and `next…PageError`; a resource keeps only the state its views read. A part of the screen with its own input, loading or errors is a nested `@Observable` model inside the view model, never a `…ViewModel`.
- **Views.** `XView` owns the view model as its only `@State`, puts it in the environment, starts every load and applies what every state shares. `XStateView` shows the content whenever there is data, otherwise the error, progress or the empty state. `XContentView` lays out the values it's given. Views that read state or act read the view model from the environment; display views take values.
- **Screen state** lives in the view model, what's presented and what a sheet edits included. A view's own `@State` holds only mechanics no test needs, such as a carousel's page.
- **Navigation.** A feature lists where its views go in its `XDestination`, carrying IDs; the places several features open are `CoreDestination` cases in CoreUI. The app maps each case to a screen in `Destination`, and registers each type at the root of every stack.
- **Composition.** `XApp.init` builds the client and every service and injects them through environment keys; each `XScreen` reads them and builds its view model. No DI container.
- **Concurrency.** Packages build in Swift 6 mode with no default actor isolation. View models are `@MainActor`, services `Sendable`, live service methods `@concurrent`, and stateful services and mocks actors.

## Gotchas

- Register `navigationDestination` only at stack roots. Inside a feature screen it registers again when that screen appears twice in one stack, and SwiftUI reports a duplicate.
- Start loads from `.task` on `XView`, never on the progress view, which goes away when the first data arrives and cancels the loads still running.
- A cancelled request must reach the view model as `CancellationError`, not as an error to show. URLSession reports it as `URLError(.cancelled)`, so the client converts it; otherwise a screen left mid-load comes back showing an error.
- Coming back to a screen runs its `.task` again. A screen with a paged list guards `load()` on that list (`guard sections.isEmpty else { return }`) and pulls to refresh through `refresh()`, or the pages already loaded are lost.
- A load for a key that's no longer current, such as a season or search words, drops its result and leaves `isLoading…` to the current key's load: a response can arrive before its cancellation.
- `XScreen` builds the view model on every `body` pass and `XView` keeps only the first, so a view model's `init` only assigns.
- A view that reads a view model the environment doesn't have crashes at runtime, so a preview of any view below `XView` injects one.
- A string literal in a package looks in the app's bundle unless it passes `bundle: #bundle`; use the catalog's generated symbols instead.
- Never set `.defaultIsolation(MainActor.self)` in a package: generated OpenAPI code doesn't build under it, and domain types must stay nonisolated.

## Workflows

Copy the checklist for the task into your response and check items off as you go.

**Add a feature**

```
- [ ] Create Packages/X with XCore, XUI, XLive, XTests (template in modules.md)
- [ ] XCore: domain models, XError, and per screen a service protocol and its mock + `.mock`
- [ ] Networking: add the endpoints to openapi.yaml and a client method for each
- [ ] XLive: a live service per protocol, mapping responses to the domain and TMDBError to XError
- [ ] XUI: XViewModel, XView, XStateView, XContentView, XDestination, Localizable.xcstrings; places another feature already links to, such as a movie's details, are pushed as `CoreDestination`, not added to XDestination
- [ ] XTests: view model tests with actor stubs, mapping tests
- [ ] App: add the local package to the Xcode project and link XCore, XUI and XLive to the app target
- [ ] App: for each service protocol, add the environment key, build the service in XApp.init, inject it on the Scene
- [ ] App: add XScreen(s), Destination cases + Destination.init(_: XDestination), DestinationView cases
- [ ] App: register XDestination at the root of every stack that can show the feature
- [ ] Build the feature's scheme and the app, and run the feature's tests; fix and repeat until both pass
```

**Add a screen to an existing feature**

```
- [ ] XCore: the screen's service protocol and mock; XLive: its live service
- [ ] XUI: view model + views; add a case to XDestination; push it with NavigationLink(value:)
- [ ] App: environment key, build the service in XApp.init and inject it
- [ ] App: XScreen that reads the service and builds the view model
- [ ] App: Destination case, Destination.init mapping, DestinationView case
- [ ] If the screen is reachable from a stack that didn't show this feature before, register XDestination there
- [ ] Build the feature's scheme and the app, and run the feature's tests; fix and repeat until both pass
```

**Add search**: pick the case that fits.

- Search across the app (a Search tab, a search screen) → its own screen, usually its own feature, with its own service, view model and views.
- Searching what a screen already shows → filter the loaded values in XContentView; no new resource or service.
- Searching the server within one screen's scope → a mode: a `SearchSession` nested in XViewModel and made with the screen's service, with its own state and content views, picked in XStateView's first branch.

**Link one feature to another** (Movie opens Trailers)

```
- [ ] If the place is a `CoreDestination`, push it and stop here. If another feature's XDestination already has it, move that case to `CoreDestination`, with its mapping, and push that
- [ ] Source feature: add a case to its XDestination in its own words (`.trailers(movieID:)`) and push it with NavigationLink(value:)
- [ ] If the source needs data the target owns (does this movie have trailers?), declare a port in the source's XCore with a mock, and implement it in an app adapter
- [ ] App: map the new case in Destination.init(_: SourceDestination) to the target's app screen
- [ ] App: register the target's XDestination in every stack that can reach it, directly or through other features (usually every tab)
- [ ] Build both features' schemes and the app; fix and repeat until they pass
```

**Decide where a type belongs**

1. Used by one feature? It stays in that feature: XCore for models and contracts, XUI for anything visual or localized, XLive for mapping and persistence.
2. A second feature needs the same concept and both must change together? Pure model → Core. A view that renders Core types → CoreUI.
3. Only looks alike? Duplicate it.
4. Purely visual and domain-free? DesignSystem.
5. Talks to the API? Networking, mapped in XLive.
6. Wiring two features together? The app.
