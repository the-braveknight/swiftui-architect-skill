# SwiftUI Architect

Decides where code lives, who owns it, and the shape of the pieces that hold an app together: modules, domain models, services, view models, the views a screen is made of, composition and routing. For how to write SwiftUI or concurrency code itself, defer to the skills in [Related skills](#related-skills).

Names: `X` stands for a feature (`Discover`, `MovieDetail`), or for a screen when a feature has several (`MovieCast` → `MovieCastService`, `MovieCastViewModel`, `MovieCastView`, `MovieCastScreen`). A *screen* is one navigable page: the feature exports its view, and the app composes it in an `XScreen`. The running example is a movie browser on the TMDB API.

## The shape

```
App target              composition root: services, screens, routing
│
├── Feature packages    one per capability (Discover, Search, MovieDetail, …)
│     XCore     domain models, errors, a service protocol and mock per screen
│     XUI       view models, views, XDestination, strings
│     XLive     live services: API responses → domain models
│     XTests    view model and mapping tests
│
└── Shared packages
      Core          domain vocabulary several features share (Foundation only)
      CoreUI        views several features show, built on Core and DesignSystem
      DesignSystem  domain-free tokens, styles and components
      Networking    the API client, generated by Apple's swift-openapi-generator
```

## Dependency direction

Each module may import only what its arrow points at. Nothing points back up, and features never point at each other.

```
App ──────► XCore, XUI, XLive, Core, DesignSystem, Networking
XUI ──────► XCore, Core, CoreUI, DesignSystem
XLive ────► XCore, Core, Networking
XCore ────► Core
XTests ───► XCore, XUI, XLive, Core, CoreUI, Networking
CoreUI ───► Core, DesignSystem
Core, DesignSystem, Networking ──► Apple frameworks and their own dependencies only
```

Hard rules:
- A feature never imports another feature. Navigation between features goes through the app; a feature that needs another's data declares a port the app implements.
- XCore never imports SwiftUI or Networking. Domain models describe what the app shows, not what the API returns.
- Generated API types never leave XLive. Live services map them to domain models, and transport errors to the feature's errors.
- DesignSystem knows no domain: no feature models, services or destinations.
- The app is the only module that sees every feature, so it is the only place features meet.

Targets, folders, Package.swift, Core, CoreUI and DesignSystem: [references/modules.md](references/modules.md).

## Who owns what

| Concern | Owner |
|---|---|
| Domain models, errors, a service protocol and mock per screen | Feature: `XCore` |
| Live services, mapping API responses and errors to the domain | Feature: `XLive` |
| View models, views, strings, where its views can go (`XDestination`) | Feature: `XUI` |
| The generated API, the client over it, error classification | `Networking` |
| Building the client and services, injecting them | App: `XApp.init`, through the environment |
| Building a screen: reading services, creating view models | App: one `XScreen` per screen |
| Navigation state, and which screen each destination shows | App: `Router`, `Destination`, `DestinationView` |
| Sheets, covers and alerts | The presenting feature view, as `@State` |

## Principles

1. **Features own their screens' views; the app composes and routes them.** A feature never builds or shows another feature's screen.
2. **Models speak the app's language.** Each is shaped for what a screen shows and can't hold an illogical value; the API's shape stops at XLive.
3. **Services do the work; view models hold state.** A service returns view-ready domain values; a view model assigns them and manages loading, errors and paging.
4. **Feature views stay plain and native.** They receive a view model, render it, and push values with `NavigationLink(value:)`. No routers, navigation closures or service lookups in feature views.
5. **Duplicate before you share.** A type moves to Core or CoreUI only when a second feature needs the same concept and both copies must change together.
6. **Every module builds, previews and tests on its own.** XCore ships a mock of each service, so XUI needs nothing else.
7. **Native SwiftUI, nothing invented.** No navigation libraries, DI containers, wrapper views around stacks, or infrastructure the app doesn't need.

## Domain and services in one page

- Domain models are `Equatable`, `Sendable` value types shaped for what screens show. The whole thing is a plain noun (`Movie`); what a list shows of it adds `Summary` (`MovieSummary`). Each is complete for its role and states each fact once, so an illogical value can't be written.
- Each feature has its own error enum, cased by what its screens show (`offline`, `notFound`, `unavailable`). Errors are never shared, and an empty answer is never an error.
- XCore declares a service protocol per screen, holding only what that screen loads. Names follow the Swift API Design Guidelines: the protocol is the role's noun, reads are noun phrases for what they return, and changes are verbs.

```swift
public protocol MovieDetailService: Sendable {
    /// - Throws: `MovieDetailError`. Cancellation propagates as `CancellationError`.
    func movie(id: MovieSummary.ID) async throws -> Movie
    func cast(movieID: MovieSummary.ID) async throws -> [CastMember]
}
```

- XLive's `TMDBMovieDetailService` calls the networking client in `@concurrent` methods, maps the response to the domain and the transport error to `MovieDetailError`. XCore's `MockMovieDetailService` (`.mock`) serves previews.
- Networking generates the API with Apple's swift-openapi-generator, wraps the generated client in `TMDBClient`, and rethrows every failure as `TMDBError`, or as `CancellationError` when the request was cancelled.

Models, errors, services, naming, ports: [references/domain.md](references/domain.md). The networking package: [references/networking.md](references/networking.md).

## View models in one page

- `@MainActor @Observable public final class XViewModel`, built by the app with IDs and services. Its `init` does assignments only. State is `private(set)`; actions are internal verbs (`load()`, `loadNextSectionsPage()`).
- Each resource has its data, `isLoading…` and `…Error`; a paged one adds `next…Page`, `isLoadingNext…Page` and `next…PageError`. Each error property has its own type.
- A screen with several resources gets computed `isLoading` and `error`, never stored. `load()` runs independent loads side by side and dependent ones after what they need.
- Cancellation is never a failure: catch `CancellationError` and keep the data and the error. Then the feature's error, then a fallback case.
- A thing and its paged list are two resources, not a value paged as a whole.

The proposed loading shape, pagination, focused models and tests: [references/view-models.md](references/view-models.md).

## Views in one page

- `XView` (public) owns the view model as `@State`, applies screen modifiers, runs `load()` from `.task`, and renders `XStateView`.
- `XStateView` shows the content whenever there is some, the error only when there's nothing to show, and progress otherwise. It switches over the error and shows CoreUI's `ContentUnavailableView` presets; an empty state appears only where the design has one.
- `XContentView` lays out the content in its scroll container, one view per resource or section. Display views take values; a view takes the view model only to read state of its own or call it, like a paging footer.
- Each is its own file. No closures passed down for view-model actions; toolbars are `ToolbarContent` structs.

Shapes, paging footer, passing data, structure rules: [references/views.md](references/views.md).

## Composition and routing in one page

`XApp.swift` builds the client and every service in `init()`, keeps them as `let` properties typed as protocols, and injects them on the `Scene`. App `XScreen` views read them and build view models; tab-root screens own their `NavigationStack`. No DI container.

```swift
.environment(\.discoverService, discoverService)
.environment(\.movieDetailService, movieDetailService)
.environment(\.movieCastService, movieCastService)
```

A feature declares everywhere its views can go in its own `XDestination`, carrying IDs; the app maps each case to a screen once, and registers each destination type at the root of every stack that can show it:

```swift
public enum MovieDetailDestination: Hashable, Codable, Sendable {
    case movie(id: MovieSummary.ID)
    case cast(movieID: MovieSummary.ID)
    case person(id: Int)
}

NavigationStack(path: $router[.discover]) {
    DiscoverView(viewModel: DiscoverViewModel(service: discoverService))
        .navigationDestination(for: MovieDetailDestination.self) { destination in
            DestinationView(destination: Destination(destination))
        }
}
```

Register only at stack roots, never inside a feature screen: a screen that appears twice in one stack would register twice, which SwiftUI reports. App file shape and `XScreen`: [references/composition.md](references/composition.md). `XDestination`, `Router`, `Destination` and push or present: [references/navigation.md](references/navigation.md).

## Concurrency

Out of scope here; use a concurrency skill. The architecture assumes:
- Swift 6 language mode everywhere, with `NonisolatedNonsendingByDefault`, `InferIsolatedConformances` and `MemberImportVisibility` in packages.
- Packages have no default actor isolation and no `nonisolated` workarounds or unchecked escape hatches. View models and their tests are explicitly `@MainActor`; services are `Sendable`; live service methods are `@concurrent`; stateful services, mocks and stubs are actors.
- The app target may use MainActor default isolation, since it is only SwiftUI composition.

## Workflows

**Add a feature**

```
- [ ] Create Packages/X with XCore, XUI, XLive, XTests (template in modules.md)
- [ ] XCore: domain models, XError, and per screen a service protocol and its mock + `.mock`
- [ ] Networking: add the endpoints to openapi.yaml and a client method for each
- [ ] XLive: a live service per protocol, mapping responses to the domain and TMDBError to XError
- [ ] XUI: XViewModel, XView, XStateView, XContentView, XDestination, Localizable.xcstrings
- [ ] XTests: view model tests with actor stubs, mapping tests
- [ ] App: add the local package to the Xcode project and link XCore, XUI and XLive to the app target
- [ ] App: for each service protocol, add the environment key, build the service in XApp.init, inject it on the Scene
- [ ] App: add XScreen(s), Destination cases + Destination.init(_: XDestination), DestinationView cases
- [ ] App: register XDestination at the root of every stack that can show the feature
- [ ] Build the feature scheme and the app; run the feature's tests
```

**Add a screen to an existing feature**

```
- [ ] XCore: the screen's service protocol and mock; XLive: its live service
- [ ] XUI: view model + views; add a case to XDestination; push it with NavigationLink(value:)
- [ ] App: environment key, build the service in XApp.init and inject it
- [ ] App: XScreen that reads the service and builds the view model
- [ ] App: Destination case, Destination.init mapping, DestinationView case
- [ ] If the screen is reachable from a stack that didn't show this feature before, register XDestination there
```

**Link one feature to another** (MovieDetail opens Trailers)

```
- [ ] Source feature: add a case to its XDestination in its own words (`.trailers(movieID:)`) and push it with NavigationLink(value:)
- [ ] If the source needs data the target owns (does this movie have trailers?), declare a port in the source's XCore with a mock, and implement it in an app adapter
- [ ] App: map the new case in Destination.init(_: SourceDestination) to the target's app screen
- [ ] App: register the target's XDestination in every stack that can reach it, directly or through other features (usually every tab)
```

**Decide where a type belongs**

1. Used by one feature? It stays in that feature: XCore for models and contracts, XUI for anything visual or localized, XLive for mapping and persistence.
2. A second feature needs the same concept and both must change together? Pure model → Core. A view that renders Core types → CoreUI.
3. Only looks alike? Duplicate it.
4. Purely visual and domain-free? DesignSystem.
5. Talks to the API? Networking, mapped in XLive.
6. Wiring two features together? The app.
