# Networking

One package talks to the API. It holds the API's types and the app's client over them, and classifies every failure once. Only the Live targets, XTests and the app import it.

## The package

```
Packages/Networking/
├── Package.swift
├── Sources/Networking/
│   ├── openapi.yaml                   the endpoints and schemas the app uses
│   ├── openapi-generator-config.yaml
│   ├── TMDBClient.swift               the app's client over the generated one
│   ├── TMDBError.swift                transport failures, classified once
│   └── Middleware/                    only what the API requires, such as auth
└── Tests/NetworkingTests/
```

- The API's types and a client come from an OpenAPI document, generated by Apple's [swift-openapi-generator](https://github.com/apple/swift-openapi-generator) build plugin (`types` and `client`, `accessModifier: public`, `namingStrategy: idiomatic`). Generated code is never committed.
- `openapi.yaml` describes only what the app uses. An endpoint goes into it before any code calls it; a large upstream spec is trimmed by hand or with the config's `filter:`.
- An API without an OpenAPI document gets the same package with hand-written `Decodable` types and a client over `URLSession`, and an app that already has a client moves it here. Either way, the rest of this file holds.
- The API's types are `public` because the Live targets in other packages map them. That makes them reachable, not shared: they never appear in an XCore model, a service protocol or anything above the Live targets.

## The client

`TMDBClient` is a `Sendable` struct over the generated `Client`. It's the app's map of the API: one method per operation the app calls, returning the API's types for XLive to map.

```swift
public struct TMDBClient: Sendable {
    private let client: Client

    public func movieDetails(id: Int) async throws -> Components.Schemas.MovieDetails {
        switch try await client.movieDetails(path: .init(movieId: id)) {
        case .ok(let response):
            try response.body.json
        case .undocumented(let status, _):
            throw TMDBError.unexpectedStatus(status)
        }
    }
}
```

- Methods keep the spec's operation names (`movie-details` → `movieDetails(id:)`), so the client reads like the spec it wraps. Swift naming starts at the domain ([domain](domain.md#naming-services-and-their-methods)).
- Each method handles every documented response, with no `default`, so a response added to the spec fails to build until it's handled.
- An API that wraps every payload in an envelope (`{ "data": … }`) is unwrapped here, so XLive maps the payload itself.
- The app builds the client with a URL session; tests build it over a stub transport.
- Middleware holds only what every request needs and the API requires, such as an auth header or a language parameter.

## Errors and cancellation

Every client method throws either `TMDBError` or `CancellationError`. XLive maps `TMDBError` into the feature's error, and view models treat `CancellationError` as "nothing happened".

```swift
public enum TMDBError: Error, Equatable {
    /// No connection, or it dropped during the request.
    case offline
    /// The request didn't complete for another reason, such as a timeout.
    case requestFailed
    /// The server answered with something that couldn't be decoded.
    case invalidResponse
    /// A status the spec doesn't document, such as 404.
    case unexpectedStatus(Int)
}
```

- Failures are classified once, in the client, so live services never see `URLError` or the generated runtime's `ClientError`.
- A cancelled request arrives as `CancellationError`, though URLSession reports it as `URLError(.cancelled)` and a cancelled task can fail in other ways too. Reported as a failure, it would show an error on a screen the user left mid-load.
- Only a lost connection is `.offline`. A timeout doesn't prove the device is offline.

## Testing

`NetworkingTests` drives the client through a stub transport: the requests it builds, the responses it decodes, and the classification, cancellation included. Features never test the network; their XLive tests map hand-built API types ([testing](modules.md#testing)).
